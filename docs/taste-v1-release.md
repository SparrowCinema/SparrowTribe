# 趣味评分 V1：数据与发布说明

## 契约

沿用 PR #284 的 `fun` / `bore`，分别为整数 0–5；`0` 是真实评分，缺失或 `null` 是未评。两项独立，不代替既有 `r`（五星十分制），也不改印章、观影次数、排片或存储键。

新增 `tasteAt`（各维度更新时间及撤销标记）与 `tastePublic`（明确公开意愿）。字段级合并保留旧客户端修改十分制评分时未携带的趣味字段。较新的撤销不会被旧值复活；整部影片的删除仍沿用现有删除标记。备份、恢复、网页同步码、微信私有 `plan` / `psync` 共用清理与合并规则。微信私有 plan 更新使用事务，保留已有排片。

四象限保持原 PR 命名：漫长难熬、迷人又折磨、平静无波、趣味横生；任一维度为 3 时暂不归类，缺一项不入图。坐标相同的影片合并成可点选的点，展开片单后进入影片页。社区图使用同时评价两项的同一批样本计算坐标，避免把不同群体的单项均分混成一个点。

## 社区与个人资料的边界

默认仅自己可见。标记看过并至少评价一项，连接同步码后，可主动发布到社区。修改公开的评分会替换原票；撤回或移除观影记录后撤销该票。公开评分不包含观影日期、场次、姓名、照片或十分制明细。

`st_taste_read` 只返回影片级汇总：有趣和无聊分别计算样本数与均分；各维度满 3 份才显示均分。社区图要求至少 3 份双维评价，并使用配对样本均值。

`st_taste_vote` 使用现有高熵同步码证明档案访问权，验证云端存在该影片的看过记录。一份档案每片一票；持有同一同步码的设备是同一个贡献者。同步码仅通过 HTTPS 请求体发送，公开查询不返回它；数据库仅保存带服务端随机盐的摘要。原始选票、盐、限流记录不授予 anon/authenticated 读写权限。

事务、版本号及幂等重试避免重放或并发产生重复票。限制每档案每分钟 20 次、每日 180 次，以及每来源每分钟 300 次；来源只保存摘要。匿名/免注册模式不能证明“一人一号”，不能声称彻底防刷。必要时可再加验证码与人工治理。公网 API key 沿用现有 publishable key，不能把 service-role key 放入网页或小程序。

停止同步或清空私人档案不会自动撤回社区评分；界面在操作前明确提醒先到影片页撤回。仍持有原同步码的用户可以重新连接并撤回；同步码丢失后无法自助证明原票归属。

离线操作写入本机独立 outbox；网络失败显示待上传，不伪装上传成功。重新联网、同步成功或手动重试时继续提交。outbox 中的同步凭据仅在本机保管，不进入个人备份或公开返回。

## 部署步骤

1. 在现有 Supabase 项目执行 `backend/taste-v1.sql`，再执行 `backend/taste-films.sql`。迁移幂等；不修改现有私人档案表。保留 `sparrow_taste` 为非公开 schema，不把该 schema 加入 Data API 的 exposed schemas。
2. 执行 `SPARROW_TASTE_LIVE=1 node tools/check-taste-live.js`。此检查仅创建自己的临时测试档案，验证一次投票的新增、重复提交、修改、撤回；finally 撤回测试票并清空测试档案，不打印同步码。不可在普通 CI 自动对生产执行。
3. 部署微信云函数 `plan`、`psync`、新增的 `taste` 到 `cloud1-d9gvudh6vc59007ac`，均选择上传并安装依赖。保持 `plans`、`psync_bind` 只能由云函数访问，不能为了社区评分开放私人集合。`taste` 的微信写操作验证 OPENID 与同步码绑定，读取则只请求公开汇总。
4. 在微信开发者工具预览：标记看过、分别评 0/5、编辑十分制/日期/版本、再看一次、切换四象限、点选重叠影片、离线重试、通过同一同步码与网页往返、撤回后确认公共人数恢复。检查窄屏和横屏、中英文、深浅色。
5. 上传小程序新版本、提交审核、审核通过后发布；仓库合并不会自动发布微信页面或云函数。网站由原 GitHub Pages 工作流发布。
6. 每次加入新影片后重建/执行影片名单 SQL；迁移只允许名单中的实际影片，活动不参与评分。未登记的影片可保留个人评分，但社区会拒绝写入。
